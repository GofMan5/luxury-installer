# Security policy

Luxury Installer handles untrusted archives and mutates user files. Please report suspected vulnerabilities privately instead of opening a public issue with exploit details.

## Reporting

Use GitHub's private vulnerability reporting for this repository. Include the affected revision, platform, reproduction steps, expected invariant, observed impact, and any proof-of-concept package. Do not include secrets or unrelated personal data.

## Scope

Security reports are especially useful for package parsing, path aliases or traversal, symlink/reparse/hardlink races, rollback and crash recovery, receipt ownership, downgrade handling, privilege transitions, signing, and updater trust.

The current `0.1.x` series is development software. Unsigned `.luxpkg` integrity checks do not authenticate a publisher. Signed v2/v3 packages require an external trust anchor; the packaged Tauri runner deliberately does not trust a co-packaged public key and currently accepts unsigned v1 only. V3 rotation requires A's exact-manifest package signature, B's proof over the package/version/A/B context, an installed trusted-A receipt, and strictly greater SemVer precedence. Setup preparation is read-only; the Rust Tauri shell owns package/root authority. Capacity preflight uses caller-visible native filesystem snapshots and conservative headroom, but does not reserve blocks or prove later writes will succeed. Private-state policy is scope-explicit: Windows user state has a protected user/SYSTEM/Administrators DACL, Windows system state requires elevation with SYSTEM/Administrators-only DACL and ownership, and Unix system state requires root-owned `0700/0600`. Install/upgrade rollback deletes the same opened object it hashed instead of resolving the pathname again; pathname directory creation, pathname/reparse parent binding outside the guarded Windows launch path, generic create/delete sync, mapped writers, and other hostile same-user races remain in scope. Maintenance uninstall is pathless and receipt-driven. Runner evidence schema v2 records packaged hashes/lifecycle checks but is unsigned and is not provenance attestation. No release should be treated as production-ready until platform-native signing, hostile-filesystem hardening, and native cancellation/recovery/signature gates are published.

Ordinary CLI/stdio engine authority remains user-only; explicit system engine/platform adapters exist only inside the privileged composition root. Windows system install, uninstall, and receipt-owned launch run through an action-separated one-shot elevated Rust helper with UAC/token and Authenticode peer checks, package-specific fingerprint/duplicated-handle binding, OS-derived fixed roots, strict private state, bounded aggregate progress and cooperative pre-commit cancellation. Before any authenticated `runas`, the shell opens the exact helper as a single-link non-reparse file with write/delete sharing denied, compares its embedded Authenticode leaf certificate with the process-image-bound signer of the running Tauri launcher, and retains that guard through `ShellExecuteExW`. Launch does not inherit helper elevation: the adapter validates the receipt/hash under system authority, duplicates the authenticated unelevated Tauri token, rejects elevated parent/primary tokens, and uses `CreateProcessWithTokenW` with no arguments. The shared Windows launch adapter opens every absolute parent component as a non-reparse directory without delete sharing and retains that chain through process creation. Linux uses a fixed root-owned helper, exact polkit policy, per-frame kernel credentials and one `SCM_RIGHTS` package descriptor. After receipt/hash/mode verification, Linux user and system launch execute `/proc/self/fd/N` for a duplicated verified entrypoint descriptor; system credentials are dropped before exec and no original-path fallback exists. macOS uses an SMAppService LaunchDaemon, socket-activated seqpacket, `LOCAL_PEERTOKEN`, strict app/helper designated requirements, one FD bound to the signed app resource, and kqueue exit observation. Linux/macOS launch clear inherited authority and drop to the authenticated account before direct application execution. Signed-final Windows, installed-polkit Linux, and signed/notarized macOS runtime evidence remain absent.

The renderer is constrained by an exact Tauri capability file: event listen/unlisten, window dragging, and named application commands only. It has no generic shell, filesystem, dialog, opener, or process permission. Native dialogs/opener calls and backend spawning stay in Rust. Production CSP permits local assets and Tauri IPC without inline script/style exceptions; Vite loopback/WebSocket and inline development styles exist only in `devCsp`. This narrows the renderer boundary but does not make a compromised same-user host trusted. On Windows the shell keeps a no-reparse backend handle with write/delete sharing denied through `Command::spawn`, closing replacement of that pathname during process creation. The bundled Studio packager and payload-free template are structurally/hash checked during assembly and use, but an unsigned portable Studio does not cryptographically bind those sidecars to its launcher. Unix still resolves the executable pathname at spawn, and a portable same-user resource may already have been replaced before validation; signed/protected native containers remain the release trust boundary.

Windows artifact verification exercises a separate one-shot local named-pipe probe against the exact packaged backend. The pipe uses a CSPRNG name, first-instance and remote-client rejection; the server binds the client to the exact launched child PID reported by the kernel, while the backend checks the kernel-reported server PID and operation ID. Frames are strict, message-bounded to 4 KiB and polled under 15-second deadlines; the parent requires child exit. Optional headless QA additionally launches through `ShellExecuteExW("runas")`, retains the process handle and requires both parent and helper `TokenElevation` checks. Every elevated launch pins the pathname through process creation; authenticated launches additionally require pre-UAC signer equality with the running Tauri image. After launch, the authenticated variant opens each kernel-reported image pathname without write/delete sharing and requires `NtQueryInformationProcess(ProcessImageFileMapping)` to prove that handle is the file object backing the running process before WinTrust. It then compares the exact SHA-256 of both verified leaf-certificate DER values. Renaming a running executable and placing another signed file at its old pathname therefore fails closed; catalog-only, unsigned, invalid, or different signers also fail. The name/PID are routing data, not secrets. This probe remains non-mutating; the separate action-bound helper path executes system preparation, install, uninstall and receipt-owned launch.

Release Setup compilation receives one exact lower-hex package review fingerprint from `xtask`; Studio explicitly removes that build environment. The Rust shell compares the embedded value with the fully inspected package before UAC. For every system action it opens that package as a regular single-link non-reparse file while denying write/delete sharing and keeps the handle alive. After PID/token/signer authentication, the elevated helper duplicates that handle from the authenticated parent process and independently opens the bundle, requiring unsigned format v1, exact package ID/review fingerprint, host target and `scope=system`; roots are derived locally from Windows Known Folders. No package path, root, key, entrypoint or request JSON is placed in argv/env/temp. Authorization returns the read-only `prepare_system_install` outcome so initial/retry maintenance state reflects the protected receipt. Install/uninstall/launch frames cannot cross-complete each other; mutation actions emit bounded aggregate events and launch returns only package ID/status. Closing Setup first closes the start/close race, waits for `starting` to publish `active`, requests correlated cancellation, and waits for terminal rollback/cleanup; one timeout budget includes a contended bootstrap lock. Signed-final lifecycle evidence remains unverified.

Engine scope authority is explicit. Ordinary install/prepare/uninstall/launch constructors authorize only `user`; dedicated system constructors preserve `scope=system` receipts and are intended solely for the authenticated helper composition root. A normal CLI/stdio process therefore rejects a system manifest or receipt even if the caller points it at system paths.

The standalone Tauri lock currently has no ordinary RustSec vulnerability errors, but its Linux-only Wry/GTK3 dependency graph includes `glib 0.18.5` with the informational unsoundness advisory `RUSTSEC-2024-0429`, plus unmaintained GTK3 bindings. The latest published Tauri `2.11.5` and Wry `0.56.0` still use GTK3 `0.18`; the advisory is fixed only in `glib >=0.20`, so a compatible crates.io upgrade is not currently available. Do not hide this with an audit ignore or an unreviewed fork: Linux publication stays blocked until the final shipped graph removes the advisory and is audited again. These target-specific crates are not linked into Windows or macOS artifacts.

Progress delivery is bounded at the backend boundary. Rust keeps one pending latest progress event behind a channel of 64 and a 16 ms ticker, flushes before every action/phase/result/error, then joins the ticker before terminal output. The Tauri shell validates completed counters and correlates operation events before renderer delivery. A missing Tauri bridge or backend fails closed instead of installing a development mock. These bounds protect availability and event ordering; they do not authenticate a compromised local backend.

Optional installation details are not a diagnostic-stream escape hatch: stdio exposes at most 128 authenticated relative manifest paths plus an omitted count, and Tauri cross-checks that projection against the payload total. Optional finish links are capped at four credential-free HTTPS URLs. Renderer validates their display shape but can invoke only a bounded index after a successful current-session install; the Rust shell retains the authenticated URL and calls the native opener. Other schemes, arbitrary commands, arguments, environment mutation, automatic launch, and privileged system-root disclosure remain forbidden.

Manifest schema v2 may name one exact payload entrypoint; it is independent from package trust format v1/v2/v3. Windows requires `.exe`; Linux/macOS require the owned file's executable flag. New ownership receipt v4 persists that optional path, while legacy v1-v3 receipts remain readable but cannot claim launch authority. Same-version repair requires both the file table and entrypoint to match, so changing launch authority requires a version transition.

Manifest schema v3 may carry one authenticated plain-text license. Validation caps it at 16,384 Unicode characters and 64 KiB UTF-8, permits only ordinary text plus tab/newline, and rejects ANSI-capable controls and bidi overrides before CLI/Tauri rendering. `inspect` exposes the exact text; Setup renders it escaped without HTML/Markdown. Install requires independent caller `acceptLicense` consent and fails before its platform port when absent. This proves only that the current caller supplied the consent bit; it is not identity proof, a durable legal-attestation system, or protection against a compromised renderer.

Launch is explicit and receipt-driven. Setup renderer receives only `hasEntrypoint` and submits a zero-argument intent; the Rust Tauri shell supplies its bound package ID and roots. The backend rejects pending recovery, reloads and validates the current receipt, then the platform adapter repeats those checks under package→destination locks. The target must remain a regular single-link file with exact receipt bytes and, on Unix, exact executable mode. Caller-relative human-CLI roots are converted to an absolute OS path before spawn. Spawn uses absolute install root as cwd, no shell or application arguments, and null stdin/stdout/stderr so application output cannot enter JSONL. Windows opens every absolute parent component as a real directory without delete sharing before opening the final executable, then retains that chain plus complementary no-follow final-file guards through process creation. This rejects an intermediate reparse point introduced after earlier validation and prevents parent rename/replacement until direct spawn or `CreateProcessWithTokenW` returns. Linux duplicates the already hashed descriptor and executes its kernel-owned `/proc/self/fd/N` name; system launch keeps the prior sanitized environment and drops supplementary groups/GID/UID first. CLOEXEC is cleared only in the post-fork child for shebang compatibility, so the process inherits one read-only descriptor for its own executable. Replacing the original package pathname after verification cannot select another image, and failure to execute the descriptor is terminal without fallback. Unix starts one detached reaper thread before process creation and waits for that direct child there, preventing zombies in a long-lived backend at the cost of one thread per live launched child. macOS still launches by pathname, including the system `launchctl asuser` broker. Pre-existing writable mappings, Linux/macOS working-directory retargeting, and macOS pathname ABA remain. Launch proves successful process creation, not application health or continued execution; the desktop shell therefore uses no ambiguous post-spawn timeout.

Public unattended Setup never turns argv into filesystem or execution authority. Exact parsing and the Rust backend/helper composition occur before Tauri/GTK initialization, so headless Linux needs no display server. The release runner accepts exact install/uninstall/help flags only, uses its compiled package fingerprint plus fixed native roots, requires current unsigned/license/publisher-migration consent, rejects mixed verifier or unknown flags with exit 64, and waits for the ordinary authenticated terminal lifecycle result before exit. The Windows NSIS parent forwards parameters to that parser without a shell and preserves the child's exit code.

All 12 production no-clobber renames return a must-use token so callers cannot confuse a completed namespace mutation with a successful persistence barrier. Linux/macOS open both parents descriptor-relative/no-follow; a shared lexical parent is opened once and duplicated with `F_DUPFD_CLOEXEC`, retaining the same inode. The token flushes destination then source with Linux `fsync` or macOS `F_FULLFSYNC`, retries `EINTR`, and maps `EINVAL`/`EOPNOTSUPP`/`ENOTTY` to typed unsupported without a fallback. Descriptor-relative Unix unlink uses the same sync helper. Once both parents are open, parent-path replacement cannot retarget those already-open descriptors or either flush; success proves only that both flush syscalls returned success. The source leaf remains name-bound/ABA.

Every replacement, uninstall, obsolete-file quarantine and inverse restore syncs a no-follow source handle before rename, keeps that exact handle through the move, and rechecks the moved identity/hash/size/mode/link count through a destination handle. On Windows the movable R/W handle shares read/delete but not write; the pinned read handle shares read/write but not delete and blocks destination rename/delete until the barrier completes. Unix keeps both opened inodes but does not lock the pathname namespace. Stationary survivor comparisons keep their stricter Windows delete-denying handle. Upgrade rollback sequentially sync-validates every eventual backup/survivor before deleting any new live file. A readonly or restrictive-reader Windows source fails before a new quarantine intent/rename, or before an inverse recovery rename with its existing WAL retained.

Windows still uses a zero-sized token because `MoveFileExW` requests documented `MOVEFILE_WRITE_THROUGH`; this is not parent binding or a general Windows directory-durability guarantee. Unix paths can still be substituted before parent opening or at the source leaf. Mapped writers and hostile same-user namespace races remain. A non-`EINTR` token failure drops the exact descriptors, and recovery does not replay both barriers before cleanup; a reader arriving after sequential prevalidation can still pause an idempotent partial rollback with its WAL retained. Native macOS/APFS and VM power-cut behavior remain unverified. These constraints prohibit any power-loss-safe or cross-platform-race-safe claim.

Production local transaction/recovery presence checks use fail-closed `path_present`, not `.exists()`. A dangling live receipt is treated as present/error state so installed bytes and WAL are preserved instead of entering missing-state cleanup.

Packaged lifecycle QA has per-session 120-second containment. Crash-recovery operations use fresh sessions; full post-operation tree/receipt hashing does not consume their watchdog budget. Initial-install and upgrade probes validate their live pre-crash anchor/WAL state inside the crash session. The uninstall probe watches only the exact live-anchor → rollback-backup plus journal transition before immediate containment, then performs the expensive receipt/tree/WAL validation against stable post-kill state; it does not wait for delayed coalesced progress while the mutation continues. Runner smoke hard-kills live pre-commit initial installs and v1→v2 updates with stdin open. Upgrade WAL binds the exact v1 receipt, v2 file and v1 backup; a one-file v0.9 downgrade-denied barrier proves the fresh process restored byte-identical v1 before retrying v2. Unix QA additionally proves executable v1 → non-executable v2 → executable v1 recovery across the live file, backup, WAL, receipt and exact tree. Exact v2 tree/receipt and uninstall cleanup are required.

The deterministic uninstall crash gate is also pre-commit. It commits an exact 770-file v1 tree, records raw receipt `R1` and `H1 = SHA-256(R1)`, then triggers containment as soon as uninstall has moved the 16 MiB anchor into rollback storage and created its journal. Stable post-kill validation requires the live receipt to remain exact `R1/H1`; the bounded WAL must start with an exact v4 uninstall header carrying `previous_receipt_sha256=H1`, every later record must be a unique `restore_file` whose path, digest and executable flag match `R1`, and `Committing` is forbidden. Fresh `prepareInstall` must then return `recoveryRequired`; the v0.9 barrier performs recovery and returns `downgrade_denied` before any new install mutation, leaving exact v1 and raw `R1/H1` for the post-cutover gate below. Automatic uninstall recovery requires this receipt-bound header: legacy-v2 uninstall state and unbound v3/v4 uninstall state fail closed before the ownership receipt or installed payload can be changed.

A separate packaged gate covers a narrower post-cutover restart path without modifying production. After the pre-commit kill/recovery has restored exact v1 and raw `R1/H1`, an external watcher scoped to `xtask` creates and syncs one unexpected state-transaction blocker as uninstall starts. Uninstall must return exact success for all 770 files, then cleanup must fail closed before mutation because its layout contains the blocker. The retained state must have no live receipt, byte-identical `receipt.deleted=R1/H1`, a complete receipt-bound WAL with exactly 770 unique matching `restore_file` records and one final `Committing` without a torn tail, the complete exact backup tree, and no other unexpected entry. Fresh `prepareInstall` must return `recoveryRequired` while leaving this state byte-identical. After removing the blocker, a fresh pathless uninstall must emit only `recovering -> loadingReceipt -> completed`, return exact `notInstalled`, and clean to locks only. No production hook, JSONL method, or dependency was added.

That evidence is strictly restart/roll-forward from fully intact committed state after deliberately deferred cleanup. Production `luxury stdio` still has no deterministic pause immediately after receipt cutover, so it is not a post-cutover hard-kill proof and covers neither partial cleanup/`journal.done` windows nor power loss/general directory durability. Windows runner publish/cleanup retries only the same `PermissionDenied` operation for 20 attempts 100 ms apart, without path/no-clobber fallback. Separate launch, cancellation, and normal lifecycle gates remain. Evidence schema v2 does not separately encode launch, recovery, or cancellation. Unix group escape remains outside containment.
